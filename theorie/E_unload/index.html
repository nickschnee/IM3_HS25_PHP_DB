Aus der Datenbank lesen

Aus zwei Tabellen wird eine Liste für das Frontend

Was bedeutet «Unload»?

Unsere Kursbezeichnung

Daten aus der Datenbank lesen und als JSON ausgeben.

  • ETL endet normalerweise beim Laden
  • Unser Projekt braucht danach einen Weg zurück ins Frontend
  • unload.php ist dieser Weg
  • Die Datei liefert Daten und kein HTML

«Unload» ist hier ein praktischer Kursbegriff und kein zusätzlicher Buchstabe in ETL.

Den Begriff bewusst begrenzen, damit er später nicht als universeller Fachbegriff ausgegeben wird.

Ein Endpunkt beantwortet eine Anfrage

GET/unload.php?city=Bern
Browser oder JavaScriptruft eine URL auf
→
unload.phpliest und formt Daten
→
JSON-Antwortgleicher Datenvertrag

Der Endpunkt ist eine normale PHP-Datei mit einer klar vereinbarten Antwort.

GET bedeutet hier: Daten anfordern, ohne den gespeicherten Stand zu verändern. Das Frontend ruft dieselbe URL später mit fetch auf.

Der Datenvertrag kommt zuerst


[
  {
    "city": "Bern",
    "year": 2023,
    "measurement_days": 92,
    "hot_days": 12,
    "max_temperature_c": 36.3
  }
]
FeldTyp
cityString
yearNumber
measurement_daysNumber
hot_daysNumber
max_temperature_cNumber oder null

Der echte Endpunkt muss dieselben Feldnamen, Typen und dieselbe Listenform liefern wie das Mock-JSON.

Think-Pair-Share: Zwei Personen vergleichen diese Struktur mit dem Transform und suchen mögliche Abweichungen.

Das Frontend braucht den Namen «Bern» und nicht den Fremdschlüssel city_id = 1.

Die Datenbank ist für konsistente Speicherung optimiert, die JSON-Antwort für einfache Nutzung im Frontend.

JOIN sucht zu jeder Sommerzeile die Stadt mit derselben Nummer.

Die Klasse sagt das Resultat der ersten Zeile voraus: Bern, 2023, 12 Hitzetage.

Nur die vereinbarten Felder lesen


SELECT
    c.name AS city,
    hs.year,
    hs.measurement_days,
    hs.hot_days,
    hs.max_temperature_c
FROM heat_summers AS hs
JOIN cities AS c ON c.id = hs.city_id
ORDER BY hs.year, c.name
  • AS city gibt dem Feld direkt den vereinbarten JSON-Namen
  • JOIN ergänzt den Stadtnamen aus der zweiten Tabelle
  • ORDER BY macht die Reihenfolge verlässlich
  • SELECT * bleibt weg, weil der Endpunkt nur vereinbarte Felder ausliefert
Die Reihenfolge ist Teil der Endpunkt-Entscheidung: zuerst Jahr, dann Stadt. Bei 258 Zeilen brauchen wir noch keine Begrenzung.

PDO macht aus Zeilen ein PHP-Array


require __DIR__ . '/../../../config.php';

$pdo = new PDO($dsn, $username, $password, $options);

$statement = $pdo->prepare($sql);
$statement->execute();

$rows = $statement->fetchAll();

$rows ist eine Liste assoziativer Arrays.

Die Schlüssel kommen aus dem SELECT.

Die Verbindung ist dieselbe wie beim Laden.

Retrieval-Frage: Woher kommen DSN, Benutzername, Passwort und Optionen? Antwort: aus derselben config.php wie im Load.

Datenbanktyp ist nicht automatisch JSON-Typ

mögliche PDO-Zeile 

[
    'city' => 'Bern',
    'year' => 2023,
    'hot_days' => 12,
    'max_temperature_c' => '36.3',
]
ohne Kontrolle im JSON 

{
  "city": "Bern",
  "year": 2023,
  "hot_days": 12,
  "max_temperature_c": "36.3"
}

Datenbanktreiber können Zahlen als Strings liefern.

Prüfe die Typen und verlasse dich nicht auf die Darstellung in phpMyAdmin.

Die Anführungszeichen um 36.3 sind der sichtbare Fehler. Chart.js wandelt manches still um, aber der Datenvertrag ist trotzdem gebrochen.

Eine Funktion hält den Vertrag ein


function normalizeSummer(array $row): array
{
    return [
        'city' => $row['city'],
        'year' => (int) $row['year'],
        'measurement_days' => (int) $row['measurement_days'],
        'hot_days' => (int) $row['hot_days'],
        'max_temperature_c' => $row['max_temperature_c'] === null
            ? null
            : (float) $row['max_temperature_c'],
    ];
}

$data = array_map('normalizeSummer', $rows);

Der Datenvertrag entscheidet über Namen und Typen der Ausgabe.

Die Funktion laut lesen lassen: Sie nimmt eine Datenbankzeile und gibt einen Datensatz für das Frontend zurück. array_map ist aus den PHP Basics bekannt.

Als JSON antworten

Der Browser bekommt Daten und sonst nichts

Die Antwort sagt, was sie enthält


header('Content-Type: application/json; charset=utf-8');
Content-TypeFormat der Antwort
→
application/jsongültiges JSON
+
charset=utf-8Zürich bleibt Zürich

Der Header muss vor jeder Ausgabe stehen.

Ein Leerzeichen oder eine Debug-Ausgabe vor header kann bereits die Meldung «headers already sent» auslösen.

json_encode macht aus dem Array JSON

PHP-Array
[ ['city' => 'Bern', 'year' => 2023] ]
→
JSON-Text
[ {"city":"Bern","year":2023} ]

echo json_encode($data, JSON_THROW_ON_ERROR | JSON_UNESCAPED_UNICODE);
  • JSON_THROW_ON_ERROR macht Kodierungsfehler sichtbar
  • JSON_UNESCAPED_UNICODE hält Umlaute lesbar
JSON ist Text mit strengen Regeln, kein PHP-Array. Die Optionen sind bewusst in Grossbuchstaben, weil es Konstanten sind.

Vier Bausteine ergeben den Endpunkt

1VorbereitenHeader und config.php
2LesenSELECT, JOIN, fetchAll
3NormalisierenFeldnamen und Typen prüfen
4Antwortenjson_encode und echo

Jeder Baustein löst genau eine Aufgabe und lässt sich einzeln testen.

Dies ist die Übergabefolie zum Code-Along. unload.php gemeinsam in genau dieser Reihenfolge aufbauen und nach jedem Schritt im Browser prüfen.

Kein Treffer ist kein Fehler

200 OK keine passenden Zeilen
[]
  • fetchAll() liefert bei null Treffern eine leere Liste
  • array_map lässt die leere Liste leer
  • json_encode macht daraus []
  • Das Frontend kann dieselbe Listenlogik weiterverwenden

Für eine Listenabfrage ist [] die stabilste Antwort.

Leere Liste und technischer Fehler unterscheiden. Für einen einzelnen Datensatz wäre 404 denkbar, unser Endpunkt liefert aber immer eine Liste.

Auch ein Fehler antwortet als JSON


try {
    // verbinden, lesen, normalisieren und ausgeben
} catch (Throwable $error) {
    http_response_code(500);
    error_log($error->getMessage());

    echo json_encode([
        'error' => 'Daten konnten nicht geladen werden.',
    ]);
}

Interne Datenbankmeldungen gehören ins Server-Log und nicht in die öffentliche Antwort.

Im Unterricht absichtlich einen Tabellennamen falsch schreiben und die zwei Orte des Fehlers zeigen: kurze JSON-Antwort im Browser, genauer Text im Log.

Kein gültiges JSON


var_dump($rows);
echo '<h1>Fertig</h1>';
echo json_encode($data);
array(258) { ... } <h1>Fertig</h1> [{"city":"Bern",...}]

Debug-Text und HTML zerstören die Antwort.

Eine reine Antwort


header('Content-Type: application/json; charset=utf-8');

echo json_encode($data, JSON_THROW_ON_ERROR);
[{"city":"Bern",...}]

Zum Debuggen das Server-Log nutzen.

Den Endpunkt filtern

Die URL stellt eine kleine Frage an die Daten

$_GET liest Werte aus der URL

GET/unload.php?city=Bern
Namecity
→
WertBern
→
PHP$_GET['city']

$city = trim($_GET['city'] ?? '');

?? '' setzt einen leeren String, wenn der Parameter fehlt.

Abgrenzung zu Extract: fetchJson sendet einen Request an eine fremde API. $_GET liest einen Parameter, den unser eigener Endpunkt erhält.

Der Filter ist optional


$sql = 'SELECT c.name AS city, hs.year, hs.measurement_days,
               hs.hot_days, hs.max_temperature_c
        FROM heat_summers AS hs
        JOIN cities AS c ON c.id = hs.city_id';

$params = [];

if ($city !== '') {
    $sql .= ' WHERE c.name = :city';
    $params['city'] = $city;
}

$sql .= ' ORDER BY hs.year, c.name';

Ohne city kommen alle Städte und mit city nur passende Zeilen.

Den SQL-Text für beide Fälle laut zusammensetzen lassen. Der Filter verändert die Auswahl, aber nie die Struktur der Antwort.

Der Wert bleibt vom SQL getrennt


$statement = $pdo->prepare($sql);
$statement->execute($params);

$rows = $statement->fetchAll();
SQL-Bauplan

WHERE c.name = :city

Werte

['city' => 'Bern']

Ohne Filter ist $params einfach eine leere Liste.

Das Muster ist dasselbe wie beim INSERT: prepare bekommt den Bauplan, execute bekommt die Werte.

Wert im SQL


$sql = "SELECT ...
        WHERE c.name = '$city'";

Anführungszeichen im Wert verändern den SQL-Text.

Der Endpunkt wird fehleranfällig und angreifbar.

Wert als Parameter


$sql = 'SELECT ...
        WHERE c.name = :city';

$statement->execute([
    'city' => $city,
]);

SQL und Wert bleiben getrennt.

Prepared Statements sind bei externen Werten Pflicht.

Keine Angriffsdemo nötig. Der Name O'Brien reicht als harmloses Beispiel dafür, dass direkt eingesetzte Werte schon fachlich brechen.

Ein Filter reicht für den Einstieg

Heute

  • ein optionaler Stadtfilter
  • eine feste Sortierung
  • immer dieselbe JSON-Struktur

Nur wenn das Projekt es braucht

  • Zeitraum mit from und to
  • Begrenzung mit limit
  • weitere fachliche Kategorien

Jeder zusätzliche Parameter braucht eine klare Bedeutung, Validierung und eigene Tests.

Die Gruppen sollen nicht vorsorglich eine allgemeine API bauen. Ein zentraler Endpunkt und ein echter Filter genügen für den Kursumfang.

Vier Aufrufe zeigen, ob der Vertrag hält

AufrufErwartung
/unload.php258 sortierte Datensätze
/unload.php?city=Bern86 Datensätze aus Bern
/unload.php?city=Zürich86 Datensätze mit korrektem Umlaut
/unload.php?city=Atlantisleere Liste []

Prüfe zusätzlich im Netzwerk-Tab den Statuscode und den Content-Type.

Die Zahlen gelten für den Hitzesommer-Code-Along mit drei Städten und 86 vollständigen Sommern von 1940 bis 2025.

Das Frontend ändert nur die URL

während das Backend baut 

fetch('data/heat-summers.json')
  .then(response => response.json())
  .then(data => drawChart(data));
mit dem echten Endpunkt 

fetch('/gruppe-3/unload.php?city=Bern')
  .then(response => response.json())
  .then(data => drawChart(data));

Wenn der Vertrag stimmt, bleibt die Verarbeitung im Frontend unverändert.

Die beiden Zweierteams vergleichen jetzt Mock-Datei und echte Antwort. Erst wenn beide gleich gebaut sind, wird die URL im Frontend gewechselt.

Übertragt das Muster auf euren Endpunkt

  • Nur Felder aus dem Datenvertrag auswählen
  • Eine feste und sinnvolle Sortierung setzen
  • JSON-Typen ausdrücklich prüfen
  • Einen optionalen Filter als Prepared Statement bauen
  • Ohne Treffer eine leere Liste liefern
  • Fehler als JSON ohne interne Details beantworten
  • Keine HTML- oder Debug-Ausgabe mitsenden
  • Mock-JSON und echte Antwort im Team vergleichen

Fertig ist der Endpunkt, wenn das Frontend ohne Sonderlösung zwischen Mock und PHP wechseln kann.

Tagesabnahme in Paaren: Eine Person aus dem Frontend-Team testet den Endpunkt einer anderen Gruppe anhand dieser Liste.
